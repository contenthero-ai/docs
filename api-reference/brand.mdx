Base URL `https://app.contenthero.ai/api/v1`. All endpoints take a bearer API key.

## Brand kit

| Method | Path | Scope | Purpose |
| --- | --- | --- | --- |
| `GET` | `/brand-kits` | `brandkit:read` | List your brand kits. |
| `POST` | `/brand-kits` | `brandkit:write` | Create a brand kit: empty, from a website (`websiteUrl` with `extract: true`), from a social profile, or as a copy. New kits start from the `standard` template. |
| `GET` | `/brand-kits/{brandKitId}` | `brandkit:read` | Read one brand kit, three ways (below). |
| `PATCH` | `/brand-kits/{brandKitId}` | `brandkit:write` | Update the kit: field content (`fields`), visual style, media, linked accounts and sections. Send `{ "archive": true }` to archive (reversible). |
| `GET` | `/brand-kit-templates` | `brandkit:read` | The templates a kit's layout comes from, and the role and load-tier vocabulary their fields use. |

### Fields, roles and tiers

A brand kit's content lives in **fields**, grouped into sections. Every field has:

- a **key**: stable and unique within the kit. Address fields by key; the user can rename a field's label, never its key.
- a **role**: what the field means (`voice.core`, `audience.profile`, `positioning.offer`, ...). Roles are the contract: the same role means the same thing in every kit, whatever the layout. `GET /brand-kit-templates` lists them all.
- a **load tier**: how eagerly it belongs in an AI's context. `core` always, `contextual` when relevant to the task, `reference` only on request.
- a **type**: `text` (a line), `textarea` (prose) or `list` (an array of strings).
- a **version**: it increments on every change. Send it back as `expectedVersion` to write safely.

### Reading a kit

`GET /brand-kits/{brandKitId}` answers one of three ways:

| Query | Returns |
| --- | --- |
| `detail=summary` | Every section and field with its key, role, tier, version and length, and **no values**. The cheap first read. |
| any of `keys`, `roles`, `sections`, `tabs`, `tiers` (comma-separated, combined with AND) | Just those fields, with values. Add `history=true` for each field's earlier versions, newest first. |
| nothing | The whole kit: sections and fields, visual identity, linked accounts and a knowledge preview. |

`detail=summary` with a filter, `history` without one, and any unknown role, tier or tab are refused with a `400` naming the valid values.

### Writing fields

Send `fields` in the `PATCH` body. Each entry is `{ key, value, expectedVersion }`, or `{ key, revertTo, expectedVersion }` to restore an earlier version (it lands as a new version, so a revert can itself be reverted). A `value` of `null` clears the field.

The write is **all or nothing**, and it lands before anything else in the patch. If any field has changed since the `expectedVersion` you sent, nothing is written and the response is a `409`:

```json
{
  "error": "1 field(s) changed since the version you read; nothing was written",
  "conflicts": [{ "key": "summary", "version": 4, "value": "The current text." }]
}
```

Re-read, reapply your change to the current value, and send the new version.

<Note>
**Removed inputs.** `businessName`, `primaryOffer`, `nicheDefinition`, `positioning`, `audience`, `voiceProfile` and `contentStrategy` are no longer accepted or returned. Sending one is a `400` that names the replacement: write the matching field with `fields`, using the keys from a `detail=summary` read.
</Note>

## Knowledge base

| Method | Path | Scope | Purpose |
| --- | --- | --- | --- |
| `GET` | `/brand-kits/{brandKitId}/knowledge` | `brandkit:read` | List the knowledge index (titles and metadata). |
| `POST` | `/brand-kits/{brandKitId}/knowledge` | `brandkit:write` | Add an item. Source is `text`, `url`, `youtube`, or a file via `fileData` (base64) or `fileUrl` (hosted). |
| `GET` | `/brand-kits/{brandKitId}/knowledge/{knowledgeId}` | `brandkit:read` | Get one item's stored body. |
| `DELETE` | `/brand-kits/{brandKitId}/knowledge/{knowledgeId}` | `brandkit:write` | Remove an item and its embeddings. |
| `GET` | `/brand-kits/{brandKitId}/knowledge/search?q=` | `brandkit:read` | Semantic search, ranked by similarity. |

<Note>
Large files and video or audio must be added by a hosted URL (`fileUrl`), which the server fetches and chunks. Base64 (`fileData`) is for small documents and images. Adding is plan-limited; a `limitReached` response means the brand kit is at its cap.
</Note>

See the [Brand guide](/guides/brand) for the structure and the knowledge workflow.
